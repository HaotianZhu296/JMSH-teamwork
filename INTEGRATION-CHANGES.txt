PART A — Data & Simulation (feature/data-simulation)
-----------------------------------------------------
Changes:
  1. Telemetry output format: CSV → JSON
     The simulator originally published each reading as a CSV line with
     Electric Motor Temperature dataset fields (stator_winding, coolant,
     ambient, motor_speed, etc.). Parts C and D expect JSON with the
     shared field names (airTemperature, processTemperature, etc.).

     Added TelemetryJson.java alongside the existing TelemetryCsv.java.
     SensorSimulator.run() now calls TelemetryJson.format() instead of
     TelemetryCsv.format(). The original TelemetryCsv class and its tests
     are preserved — no deletions.

     Field mapping applied:
       Electric Motor field     →  Unified JSON field
       ──────────────────────────────────────────────
       ambient (°C)             →  airTemperature
       stator_winding (°C)      →  processTemperature
       motor_speed (rpm)        →  rotationalSpeed
       torque (Nm)              →  torque
       (not in dataset)         →  toolWear = 0.0
       profileId, sampleIndex,    (preserved as extra fields
        coolantC, iD, iQ, uD, uQ)  in JSON for traceability)

  2. SensorSimulatorTest updated
     Three test methods that asserted CSV output now validate JSON fields
     using a regex-based helper instead of TelemetryCsv.parse().

  3. New TelemetryJsonTest
     Two tests verifying JSON structure and field mapping correctness.

PART C — Detection & Alerting (detection-alert)
------------------------------------------------
Changes:
  1. Lombok compilation fix
     Problem: Lombok 1.18.36 crashes on JDK 25 with
     "TypeTag::UNKNOWN" error. The annotation processor was also not
     configured in maven-compiler-plugin, so @RequiredArgsConstructor
     and @Builder were silently ignored — resulting in 3 compile errors.
     Fix: Added <annotationProcessorPaths> to the maven-compiler-plugin
     section of detection-alert/pom.xml. Upgraded Lombok to 1.18.48.

  2. MQTT topic mismatch
     Problem: application.yaml subscribed to "sensors/+/detections" but
     Part A publishes to "sensors/{machine_id}/telemetry". The detection
     service would never receive any messages.
     Fix: Changed mqtt.topic to "sensors/+/telemetry".

  3. MQTT authentication missing
     Problem: Part D's broker requires authentication
     (allow_anonymous false). Part C had authentication commented out
     with "// TODO: Add authentication if Mosquitto later".
     Fix:
       - Added mqtt.username=detector and mqtt.password=detect_pass_2024
         to application.yaml.
       - Updated MqttConfig.java to read the new config fields and apply
         them via MqttConnectOptions.setUserName()/setPassword().
         The auth block is conditional — if username is empty or absent,
         it connects without credentials (backwards compatible).

================================================================================
BUG FIXES (post-review)
================================================================================

1. Password Mismatch (generate-passwords.sh vs application.yaml)
   Problem: generate-passwords.sh used "det_pass_2024" for the detector
   user, but application.yaml had "detect_pass_2024". The one-character
   difference caused MQTT authentication failure for the detection service.
   Fix: Changed generate-passwords.sh to use "detect_pass_2024".

2. Spring Integration "Dispatcher has no subscribers" (Part C)
   Problem: MqttPahoMessageDrivenChannelAdapter was declared as a separate
   @Bean. Spring auto-started it with its own default output channel, but
   the IntegrationFlow created a different input channel — messages arrived
   at a channel with no subscribers.
   Fix: Removed the separate @Bean for the adapter. The adapter is now
   constructed inline within the IntegrationFlow, so the flow manages the
   adapter's lifecycle and channel wiring exclusively.

3. Alert Publishing Not Implemented (Part C)
   Problem: DetectionService evaluated sensor readings and saved results
   to SQLite, but never published alerts back to MQTT. The dashboard
   subscribed to alerts/# but nothing was writing there.
   Fix: Added an outbound MQTT flow in MqttConfig.java:
     - alertOutboundChannel (DirectChannel) + alertOutboundFlow with
       MqttPahoMessageHandler (client-id: spring-detection-service-publisher)
     - When inbound processing produces WARNING or CRITICAL status, the
       EvaluationReturn is serialized to JSON and published to
       alerts/{machineId}.
     The detector user's ACL already permits "topic write alerts/#".

4. Rotational Speed Thresholds Too Aggressive
   Problem: rotationalSpeed thresholds (warning 1500, critical 2000) were
   set for a generic predictive-maintenance dataset. The Electric Motor
   Temperature dataset has motor_speed values up to ~6000 RPM, so nearly
   every reading triggered a false warning.
   Fix: Adjusted to warning 4000, critical 5500 in application.yaml.

5. Node-RED Dashboard Package Missing
   Problem: nodered/node-red:3.1 image does not include node-red-dashboard.
   The UI widgets (chart, gauge, toast) returned 404.
   Fix: Added dashboard/Dockerfile that installs node-red-dashboard.
   Updated docker-compose.yml to build from that Dockerfile instead of
   using the stock image.

6. README Startup Commands Incorrect
   Problem: README referenced non-existent classes PipelineMain and
   EvaluationRunner. Also described anonymous broker access.
   Fix: Updated to reference actual entry points (SensorSimulator,
   EventStoreMain) and added password generation step.
